# CAN 设备接入硬约束（实测）

本文件只写**真机踩过或实测确认**的约束。每条按「症状 → 原因 → 规避」组织，
末尾给出证据，便于判断是否适用于自己的设备。

测量对象为本仓库随附的两套厂商库：
- 创芯 ZHCX：`ControlCAN.dll` 9.1.2.1（x64）
- 广成 GCAN：`ECanVci64.dll` + `CHUSBDLL64.dll`

其它厂商的接口语义可能不同，但下面这些“驱动层看起来成功、实际在污染总线/闩死设备”
的模式具有普遍性。

---

## 1. 无 ACK 时“自动重发”会泛洪

**症状**
单节点、对端只听或总线未接被测件时，发 1 帧，对端在 400 ms 内收到 1552 帧
（约 3880 fps），接收队列被灌满、判定被污染。

**原因**
ControlCAN 的 `VCI_CAN_OBJ.SendType=0` 表示“正常发送，失败自动重发”。
总线没有正常节点应答时，DLL 会持续重发，直到约 1 s 超时或发送缓存（1000 帧）灌满。
这是驱动行为，不是总线故障。

**规避**
- 默认用单次发送（ControlCAN 的 `SendType=1`），并让 api 层默认值也是 1，
  防止有人绕过 backend 直接调用。
- 只有确认总线上存在正常应答节点时，才由业务层显式要求重发；重试策略放业务层。
- 发送前确认通道不是只监听；能力描述里写清“返回成功只代表进入设备缓存，不代表被 ACK”。

**证据**
环回用例：`SendType=0` 400 ms 收 1552 帧，`SendType=1` 收 1 帧。

## 2. `DataLen>8` 会发出越界内存垃圾

**症状**
传入 12 字节，设备照发不报错；接收端 `DataLen=12`，但只有前 8 字节以内是有效数据，
其余是结构体 `Data[8]` 之后的内存内容（实测读到随机字节），总线上出现无法解释的脏数据。

**原因**
经典帧结构体只有 `Data[8]`；驱动不做长度校验，直接按 `DataLen` 拷贝，越过数组边界。

**规避**
- backend 的 `send()`：`fd`、`len(data)>8` 直接抛错，不静默截断。
- api 的发送函数再硬钳一次 `DataLen=min(8,len(data))`，只拷贝前 8 字节。
- 接收侧同样按 `min(8, DataLen)` 截断，不要把残留当有效载荷。
- FD 能力在 `open()` 阶段就拒绝，不要等发送才失败。

**证据**
ZHCX 环回用例 7；GCAN 头文件同样只定义 `Data[8]`。

## 3. 只监听通道发送“假成功”并闩死设备（ZHCX）

**症状**
`Mode=1`（只监听）通道调用发送函数返回 1，但对端收到 0 帧；
随后打开设备持续返回 0，读取板卡信息仍能成功，设备接口 `CreateFile` 也能成功
（说明没有进程占用）。软件复位返回 0；**只能拔插 USB 恢复**。

**原因**
发送任务进入了一个永远无法完成的队列，DLL/固件停留在“已打开”状态。
这是设备侧闩锁，不是进程占用，也不是驱动缺失。

**规避**
- 不启用只监听模式：`open()` 见到 `listen_only=True` 直接抛“能力不支持”，
  设备始终以正常模式初始化；`capabilities().supports_listen_only=False`。
- `send()` 仍保留防御性判断：通道只监听时绝不调用底层发送。
- 切换通道模式前先停止发送、清空队列；异常路径先复位通道再关闭设备。
- 打开失败提示里写“若刚做过非法模式切换，请拔插 USB 恢复”。

**证据**
ZHCX 只监听通道发送返回 1、对端 0 帧；随后打开持续失败，仅拔插恢复。

## 4. 厂商 DLL 跨通道非线程安全（GCAN）

**症状**
双通道同时周期发送时，两路在同一瞬间调用发送函数双双失败；
CAN1 `ErrCode=0x4000`（命令执行失败），CAN2 `ErrCode=0`；TEC/REC 均为 0，
总线侧无错误。失败只发生在两路发送时刻完全重合的那一次。

**原因**
`ECanVci64.dll` 内部无锁，厂商例程都是单线程调用，头文件与手册均未声明线程安全。
“每通道一把锁”仍允许两个线程同时进入同一个 DLL。

**规避**
- **设备级一把全局锁**串行化所有 DLL 调用（打开/关闭/初始化/启动/复位/清队列/
  发送/接收/查询队列/读错误/读状态），跨通道也是同一把。
- 锁放在 api 层每个公开方法里（可重入锁），backend 不再各自加锁。
- 多通道周期发送把相位错开（例如半个发送槽），避免同一瞬间打 USB。
- 单测用假 API 记录并发重入，断言两线程不会同时进入底层。

**证据**
双通道并发发送首次失败；加锁后同一脚本连续两次 10 s、双通道各 3600 帧全成功。

## 5. 时间戳单位：两份手册互相矛盾

**症状**
按手册换算后，算出的周期差约 10 倍（或时间戳几乎不涨/涨得过快），
固定周期表、CSV 相对时间全部失真。

**原因**
GCAN 中文手册 V5.5 写“微秒”，英文手册 V5.2 写“0.1 ms”；ZHCX 手册写 0.1 ms。
不同厂商、不同手册版本不能互相信任。

**规避**
- 必须实测定论：固定间隔发送 3~6 帧，比较“设备时间戳增量 / 主机单调时钟增量”。
  比值 ≈1 → µs；比值 ≈10 → 0.1 ms。
- 把单位写成显式常量，换算集中在 backend 一处。
- 已知结果：GCAN = 1 µs（实测 999,940 ticks/s）；ZHCX = 0.1 ms（2 s 比值 1.0003）。
- 可选：首次打开后做一次自校准并记日志；校准失败按手册值兜底并 WARN。

**证据**
GCAN 固定周期发送：6 个 ID 的 ticks/s 中位数 999,940.4；
ZHCX 2 s 时间戳增量与主机增量比值 1.0003。

## 6. 时间戳基准不是会话起点，且 32 位会回绕

**症状**
- 首帧时间戳不是 0，而是几十万到十几亿；
- 关闭再打开后时间戳继续累加，不归零；
- 长时间运行（ZHCX ≈4.97 天、GCAN ≈71.6 分钟）后，周期统计出现负值或巨大跳变；
- 导出 CSV/BLF 的相对时间出现负跳变。

**原因**
- 基准通常是**设备上电/首次被打开**，不是每次初始化；
- 字段是 `uint32`：ZHCX ×0.1 ms ≈ 4.97 天回绕；GCAN ×1 µs ≈ 71.6 分钟回绕；
- 多通道读取顺序可能让原始值短暂“倒退”。

**规避**
- 每个通道一个时间戳追踪器：按无符号差值推进；差值超过半量程视为倒退，
  保持已输出的单调值；两帧间隔超过半个回绕周期时补齐回绕次数。
- 对外交换后输出**秒**，同通道严格单调；没有硬件时间戳时回落主机单调时钟。
- 上层不要假设“首帧为 0”或“绝对时间可跨设备比较”；只用通道内间隔。
- 判定层若使用硬件到达时刻，见第 14 条。

**证据**
GCAN 首帧 1,220,383,056 µs，跨关闭/打开持续累加；
ZHCX 时间戳在设备上电后从非零值开始。

## 7. 设备被其它上位机占用时的错误码

**症状**
系统里能看到设备，但本程序打开失败；或枚举正常、一开就失败。
其它 CAN 工具在跑时，有时能打开、有时不能——取决于它是否真的占用了设备。

**原因**
同一设备只允许一个进程打开。
- ZHCX：ControlCAN 内部 `CreateFile` 返回 `ERROR_ACCESS_DENIED(5)`，打开 API 返回 0。
  某些 CAN 工具只要扫描/连接同芯片设备，即使 UI 上“断开”也仍持有句柄。
- GCAN：打开返回 0，读错误信息给 `0x0100`（设备已打开）或 `0x0200`（打开设备错误）；
  厂商工具或其它上位机占用时同样如此。

**规避**
- 枚举能看见设备、打开却失败 → 抛“设备被占用”，列出常见占用者，
  要求关闭后重试。
- 不要自动重试或强行抢占；不要用“进程是否存在”判断占用（要看是否加载了对应 DLL/句柄）。
- ZHCX 额外：读板卡信息**只能在打开成功后调用**，设备不可用时该调用可能触发 DLL 崩溃。
- 需要共存时，关闭其它工具的自动扫描/设备连接，或退出该工具。

**证据**
TSMaster 运行并扫描 ZLG 设备时，CreateFile 返回 5、打开返回 0；
GCAN 在厂商工具占用时返回 `0x0100`。

## 8. 没有枚举 API / 索引随 SN 重排

**症状**
- 换一次插拔顺序，昨天能用的索引 0 变成别的设备；
- 两台设备时按“第几个”绑定，跑着跑着绑错；
- 枚举函数不存在，或返回的型号串为空。

**原因**
- GCAN `ECanVci` 没有枚举 API，只能按“设备类型 × 索引”盲开探测；
  索引规则是“按 SN 从小到大分配”，插拔/增减设备会重排。
- ZHCX 的查找接口能返回数量/SN/通道数，但型号字段实测为空串，
  型号需再读板卡信息；老驱动可能没有该导出。

**规避**
- 设备身份只用 SN；索引仅本次打开使用。
- 多设备且用户未指定 SN → 直接报错并列出可用 SN，**不要按“第几个”猜**。
- 枚举结果按 SN 排序，保证列表顺序稳定。
- 枚举本身会开关设备：不要放在采集热路径，也不要与已打开设备并发；结果缓存，掉线/重开再重探。
- 盲开探测要有上限（如索引 0..7、类型 4 再 3），失败即停，并按 SN 去重、保留通道数多的那条。

**证据**
GCAN type 4 与 type 3 同时响应同一硬件；无枚举 API，只能盲开。

## 9. 设备信息里的通道数可能是无效值

**症状**
双通道设备被识别成 50 路（或 0/1 路），设备选择界面的通道号上限异常。

**原因**
GCAN 实测板卡信息 `can_Num=50`，字段未正确填充；不同固件行为可能不同。

**规避**
- 只采信 1/2 这种合理值；其余按型号表推（type 4 → 2，type 3 → 1）。
- 不要用该字段直接生成界面上限；打开前还要校验通道号小于真实通道数。

**证据**
GCAN 板卡信息实测 `can_Num=50`。

## 10. 接收失败返回 `0xFFFFFFFF`、默认等待参数会阻塞

**症状**
- 统计出 42 亿帧；
- 采集线程卡死，界面不刷新；
- 无数据时接收函数一直不返回。

**原因**
- GCAN 接收返回 `ULONG`，失败是 `0xFFFFFFFF`；按无符号当帧数会变成 42 亿。
- C 头里等待时间默认 `-1`（阻塞）；不同语言例程的参数个数还不一致。
- ZHCX 接收失败返回 0/负值，语义不同，不能照抄。

**规避**
- 每次读取前先查队列长度判空；接收调用显式传 `WaitTime=0`。
- 失败先判 `== 0xFFFFFFFF`（或 `<0`），读错误信息，记错误计数，**不要产生伪帧**。
- 批量上限设常量（GCAN 实测单次可取 4140 帧，但建议 ≤512，避免长时间占锁）。
- 关闭函数的参数个数按头文件（GCAN 是 2 个），不要照抄例程的 3 个参数
  （x64 忽略多余参数“看起来能跑”，x86 `__stdcall` 会栈失衡）。

**证据**
GCAN 接收失败返回 `0xFFFFFFFF`；单次读取实测 4140 帧。

## 11. 启动接口后必须等 ≥10 ms

**症状**
刚打开就发送，偶发发送返回失败或首帧丢失；重开后又正常。

**原因**
GCAN 手册 1.5.11 明确要求启动通道之后延时 ≥10 ms 才能发送；驱动/固件尚未就绪。

**规避**
- 打开流程在所有通道启动之后固定 `sleep(0.010)`，再置“已打开”状态。
- 不要在启动与首次发送之间插入其它设备的枚举/打开操作。

**证据**
GCAN 手册 1.5.11。

## 12. DLL 同目录依赖、位数与 CRT

**症状**
- `WinError 126`：找不到依赖模块；
- `WinError 193`：位数不匹配；
- 开发机可加载，换干净机器失败。

**原因**
- GCAN `ECanVci64.dll` 运行期依赖**同目录** `CHUSBDLL64.dll`；
  只拷主 DLL 必失败。
- 32 位版本与“新”64 位版本依赖 `MSVCR80.dll`；干净机器可能没有。
- ControlCAN 本身不依赖同目录 DLL，但需要系统已装 WinUSB 驱动。

**规避**
- 选依赖最少的运行库整目录随包。
- `add_dll_directory(dll_dir)` 并**保活返回句柄**；加载后校验必需导出。
- 预检 PE 头，位数不符直接报“位数不匹配”。
- 只带目标进程位数对应的 DLL；两种位数分目录并在文档写明。
- 加载失败提示要写清“主 DLL 与依赖 DLL 必须同目录”“需预装厂商驱动”。

**证据**
GCAN 64 位主 DLL 依赖同目录 `CHUSBDLL64.dll`。

## 13. 正常模式不自收；两通道是两条独立总线

**症状**
发送返回成功，但本机一帧都收不到，误判“发送失败”。

**原因**
- CAN 控制器在 Normal 模式下不会把自己发出的帧写入接收 FIFO；
- CAN1/CAN2 物理上是两条不同总线，没有跨通道回显；
- 自发自收需要环回模式或帧级自发自收标志。

**规避**
- 不承诺“发送回读”；验证发送内容要用第三节点（另一块卡/分析仪）或让被测件应答。
- 台架停机时才允许切环回模式，且需用户批准。
- 统计发送帧数时明确它是“已请求/已入缓存”，不是“已被 ACK”。

**证据**
ZHCX 正常模式无发送回显；GCAN 正常模式同样读不到自己发出的帧。

## 14. 批量轮询导致判定窗口“无响应”（到达时钟）

**症状**
被测件已回复，原始帧时间戳也在判定窗口内，但用例判“无响应”；
换成更大的窗口就能过。

**原因**
监控层把“批次读取时刻”当作帧到达时刻。批量轮询 + 背景流量时，
响应帧要晚一批才被读到，落在窗口外。这不是内容错误，也不是总线上没有响应。

**规避**
- 建立硬件到达时钟：按通道把硬件时间戳锚定到本机单调时钟，
  取最近一段时间样本的最小偏移；设备复位、回绕、长时间空闲自动重建锚点。
- 帧样本的到达时间使用真实总线到达时刻；无硬件时间戳的帧仍回落读取时刻。
- 判定层保留读取补偿余量，但判定窗口右端**固定**为“步骤开始 + 等待时长”，
  余量内只接受“硬件戳落在窗口内”的帧。
- 新后端接入后，用真实被测件的短窗口用例回归一次，不要只测大窗口。

**证据**
某响应帧实际 62 ms 到达、硬件时间戳在窗口内，但按读取时刻被排在窗口外，
最终被判“无响应”。

## 15. 远程帧标志与残留数据

**症状**
远程帧被当成数据帧；远程帧的 `data` 是上一帧的残留字节。

**原因**
- ZHCX 接收侧远程帧 `RemoteFlag=2`（发送时用 1），写 `==1` 会漏判；
- 远程帧接收时 `Data[8]` 不保证清零，实测读到上一帧内容。

**规避**
- 接收侧用 `bool(RemoteFlag)` / `!=0` 判断远程帧；
- 远程帧输出空 `data`，不要把残留当载荷；
- 发送侧远程帧按厂商要求置 1（ZHCX/GCAN 发送语义一致）。

**证据**
ZHCX 接收远程帧 `RemoteFlag=2`，`Data` 为上一帧残留。

## 16. 同名 DLL：ZLG 旧 ControlCAN 与创芯 ControlCAN

**症状**
- 代码按 `LoadLibrary("ControlCAN.dll")` 或系统搜索路径加载，换机器后功能异常、
  时间戳或通道能力对不上；
- 同一进程先加载了 ZLG/CANTest 的 ControlCAN，再调用创芯设备，函数返回成功但行为不符；
- 调试器里看到两个同名模块，实际只有一个被加载。

**原因**
- ZLG 旧 CANTest 与创芯 ZHCX 都提供 `ControlCAN.dll`，导出名兼容；
  创芯是兼容实现，不是同一份二进制。
- Windows 按“已加载模块名 > 应用目录 > 系统目录 > PATH”解析；同名时先加载者生效，
  后续加载请求直接复用已加载模块。
- TSMaster 安装目录也带 `ControlCAN.dll`（用于扫描 ZLG 设备），会加剧冲突。

**规避**
- 每个厂商独立目录，按**绝对路径**加载（如 `LoadLibraryExW` +
  `LOAD_WITH_ALTERED_SEARCH_PATH`）；不要改全局 PATH，不要把多厂商 DLL 放同一目录。
- 加载后校验文件版本/公司名/大小/导出集合，并把实际解析路径写入日志。
- 缓存键用绝对路径或厂商 ID，不要用文件名。
- 进程内尽量避免同时加载两份同名 DLL；必须共存时先做兼容性验证并固定加载顺序。

**证据**
创芯 `ControlCAN.dll` 9.1.2.1（x64 2,683,392 B）；ZLG CANTest 自带
`ControlCAN.dll` 45,056 B；TSMaster 安装目录 `bin64\ControlCAN.dll` 亦同名。

## 17. 运行库不是单文件：内核驱动目录与运行环境

**症状**
- `LoadLibrary(zlgcan.dll)` 成功，但枚举为空或打开设备失败；
- 干净机器报缺 `MSVCR120.dll` / `MSVCP120.dll`；
- 只拷 `TSMaster.dll` 能加载，但打不开硬件或找不到设备。

**原因**
- `zlgcan.dll` 运行期从同目录（或搜索路径）的 `kerneldlls/` 加载设备内核驱动与描述文件；
  缺少该目录时主库仍能加载。
- `zlgcan.dll` 依赖 VC++ 2013 运行库（`MSVCR120`/`MSVCP120`）。
- TSMaster SDK 的 `TSMaster.dll` 只是接口层；实际访问硬件依赖已安装的 TSMaster
  运行环境（`libTSMaster.dll`、`libTSH.dll`、BPL 运行包、VC 运行库等），且版本需匹配。

**规避**
- 在 README/安装检查中写清完整依赖矩阵；打包时校验“主 DLL + 依赖子目录 + CRT”，
  不只校验主 DLL。
- 启动时做“加载 + 枚举”自检，失败时指出具体缺失项。
- 不要把“`LoadLibrary` 成功”当作可部署；验收标准是能枚举并打开设备。
- 头文件、导入库、运行库、运行环境成套替换，禁止混用不同版本。

**证据**
随附 `zlgcan.dll` 导入 `MSVCR120`/`MSVCP120`；厂商 SDK 的 `kerneldlls`
x64 179 个文件/29,531,934 B、x86 178 个文件/23,226,941 B。
TSMaster 2025.8.28.1610 的 SDK `lib` 仅 3 个文件，安装目录另有完整运行库。

## 18. 其它现场约束（低频但会浪费时间）

| 现象 | 原因 | 规避 |
| --- | --- | --- |
| 参数改了不生效、收不到自己发的帧 | 设备曾被中继软件开启，配置固化在设备里 | 用厂商中继软件关闭；必要时恢复出厂 |
| 总线两端没有 120Ω，偶发错误帧 | 终端电阻缺失 | 总线两端各 1 个 120Ω；设备内置电阻按硬件说明短接 |
| 只监听模式无法做双通道自测 | 只监听节点不应答，对端会一直重发/报错 | 用第三节点；或停机时用环回模式 |
| 枚举时总线上出现异常 | 盲开探测会开关设备 | 枚举不要与采集并发；缓存结果 |
| 厂商 DLL 向 stdout 打印调试信息 | 初始化时打印索引/波特率等 | 无害；需要干净输出时在加载层重定向 |
| 配置层波特率选项不够 | 配置校验只允许少数经典档位 | 同时改校验表、界面下拉与厂商表，别只改一处 |
